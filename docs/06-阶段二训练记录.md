# 阶段二训练记录：Qwen3-0.6B LoRA SFT

> 记录截至 2026-09-30。正式训练及底座模型、三个 epoch 的 500 条教师标签评测均已完成。训练数值来自服务器终端日志；评测指标使用下载的预测文件和正式 gold 在本地复算。服务器地址、登录身份和个人目录均不在公开文档中记录。

## 1. 本阶段交付范围

本阶段将教师生成的结构化场景标签转换为 Qwen3 对话格式，对 Qwen3-0.6B 进行 LoRA 监督微调。学生任务是根据用户话语和上下文信号输出契约 JSON，包括场景、意图、复杂度、上云建议和槽位。训练只对 assistant 的 JSON 响应计算 loss。

| 输入或产物 | 数量 / 状态 | 校验依据 |
|---|---:|---|
| 正式训练源 `distill_dataset.jsonl` | 5500 条 | MD5 `d32b73adbc456212f42eaae2099d93ee` |
| 独立评测集 `eval_gold.jsonl` | 500 条 | 单点修正后 MD5 `27a33ffbf5d2dd01d391533cb0443f3c`；与训练集按 ID 互斥 |
| 50 条 SFT 冒烟数据 | 50 条 | `build_sft.py --limit 50` 输出行数核对 |
| 正式 SFT 数据 | 5500 条 | `build_sft.py` 校验输入 MD5、重复 ID 和教师 target 契约 |
| LoRA adapter | 每轮保存，共 3 轮 | 正式训练日志报告 `python exit=0`；最终目录位于项目的 `scene_ai_server/data/model_output/` |
| epoch-1 预测冒烟 | 25 条预测已生成 | `predict_lora.py` 输出 `generated 25`，预测 JSONL 经 `wc -l` 核对为 25 行 |
| 底座和三个 adapter 的 500 条预测 | 四组各 500 条 | 每组 ID 唯一且与同一份正式 gold 的 ID、顺序一致；本地复算指标与服务器报告完全一致 |

训练服务器使用正式 5500/500 批次；公开仓库 `scene_ai_server/data/` 中保留的是早期 60/40 pilot 工件。公开仓库的 pilot 报告不能当作本次正式训练的评测结果。

正式训练集按**教师 target** 统计的场景构成如下；种子文件的顶层场景不用于描述学生实际学习的标签分布。

| 场景 | 条数 | 占比 |
|---|---:|---:|
| food | 2148 | 39.1% |
| reading | 1566 | 28.5% |
| none | 646 | 11.7% |
| location | 597 | 10.9% |
| chat | 543 | 9.9% |

## 2. 环境、模型与训练配置

| 项目 | 已核对事实 |
|---|---|
| GPU | 共享 NVIDIA B200；训练前可用显存 55.6 GiB，整卡总显存 178.3 GiB；本任务按约 40 GiB 可用预算规划 |
| CUDA/PyTorch | CUDA 12.8、PyTorch `2.10.0+cu128`；系统 `base` 环境没有 PyTorch |
| Transformers / PEFT | Transformers `5.12.1`、PEFT `0.21.1`、Accelerate `1.15.0` |
| 环境隔离 | 在已有 CUDA 环境上使用继承系统包的独立 `mova-train` venv，补装 PEFT/Accelerate；训练脚本直接读取 JSONL，不依赖 `datasets` |
| 底座 | Qwen3-0.6B；本地从 ModelScope 获取，`model.safetensors` 文件大小 1,503,300,328 字节；本地 SHA-256 为 `f47f71177f32bcd101b7573ec9171e6a57f4f4d31148d38e382306f42996874b`。服务器端未在本记录中提供同一文件的 SHA-256 校验结果 |
| 产物路径 | 底座模型与训练输出分开；LoRA adapter 存在项目的 `scene_ai_server/data/model_output/`，不写入共享预训练模型目录 |

下载的 `run_config.json` 确认本轮实际使用 3 epoch、单卡 batch 8、梯度累积 4、最大长度 2048、学习率 `2e-4`、seed 42、显存 fraction 0.17、启动时空闲显存 55.63 GiB，以及总计 516 step。LoRA 和优化器设置以本轮 `train_lora.py` 脚本为准。

| 参数 | 本轮使用值 |
|---|---:|
| epoch | 3 |
| 单卡 batch / 梯度累积 / 有效 batch | 8 / 4 / 32 |
| LoRA `r` / `alpha` / `dropout` | 16 / 32 / 0.05 |
| LoRA target | `q_proj`、`k_proj`、`v_proj`、`o_proj`、`gate_proj`、`up_proj`、`down_proj` |
| 精度 / 最大序列长度 | BF16 / 2048 |
| 优化器 / 学习率 | AdamW / `2e-4`；5% warmup 后 cosine 调度 |
| 显存控制 | 开始时要求空闲显存 ≥40 GiB；PyTorch allocator 限制为整卡的 17%，约 30.3 GiB |

5500 条、batch 8 对应每轮 `ceil(5500/8)=688` 个微批次；累积 4 次梯度后每轮 `ceil(688/4)=172` 个优化 step，三轮共 **516 step**。这与正式训练日志一致。交接计划曾写 batch 16 × 累积 2；实际脚本采用 8 × 4，有效 batch 同为 32。

## 3. 实际遇到的问题及处理

| 问题与诊断证据 | 处理 | 结果与边界 |
|---|---|---|
| `base` 环境导入 `torch` 失败；CUDA 环境能导入 PyTorch/Transformers，但缺 PEFT、Accelerate、datasets | 从已有 CUDA 环境创建隔离 venv，仅补齐本轮 LoRA 所需包；训练数据由标准库 JSONL 读取 | CUDA、GPU、PEFT 导入检查通过；未为不使用的 `datasets` 额外安装训练依赖 |
| 预期预训练目录不存在；Hugging Face 下载只有约数百 kB/s | 从 ModelScope 在本地获取 0.6B 底座，再通过 WinSCP 上传到单独的模型输入目录 | 模型在 50 条冒烟和正式训练中成功加载；本记录不把“可加载”当作服务器文件 SHA-256 校验 |
| WinSCP 上传 `model.safetensors.filepart` 报 `Permission denied`，错误码 3 | 分别在 SFTP 主机与训练容器核对实际挂载目录和数字 UID/GID；按 SFTP 身份调整目标目录权限，再上传 | 问题来自 root 创建目录与 SFTP 登录账号属主不同，加上两端绝对路径不同；详见[服务器操作记录](公司服务器操作快速上手.md) |
| 首次 smoke 后 tmux 会话消失、训练进程不存在；日志中有 Python 异常，目录中没有 adapter | 从日志而非会话名称定位失败点；新建独立 tmux 会话，避免交互 shell 的错误退出设置直接结束会话；通过 `tee` 保留日志并用 `${PIPESTATUS[0]}` 核对 Python 退出码 | 会话退出与 Python 失败同时出现；无法仅凭日志证明 tmux 本身崩溃。重新运行后会话承载完整训练 |
| 首次 smoke 在 `chat_34630` 触发“generation prefix 与完整对话不一致” | 改为先核对 chat template 的**文本**前缀，再分别 token 化 prompt 和 assistant 后缀；避免要求完整串的 BPE token 序列必须共享同一前缀 | 后续通过数据集构造并进入模型加载；跨边界 BPE 合并是合理解释，但未单独做 tokenizer 内部归因实验 |
| 第二次 smoke 报 `TypeError: BatchEncoding + list` | 从 `apply_chat_template` 返回值中显式提取 `input_ids`，兼容 token ID 列表与 `BatchEncoding` | 修复后 50 条冒烟训练完成，退出码 0；正式 5500 条训练完成 |
| 预测脚本也把 `apply_chat_template` 的结果直接当 Tensor 使用 | 在 `predict_lora.py` 中统一转换 `input_ids` 和 `attention_mask`；允许不传 adapter 运行底座基线 | 服务器运行 `--help` 确认底座基线入口；epoch-1 的 25 条冒烟和四组各 500 条正式预测均完成，评测结果见第 5 节 |
| WinSCP 递归下载训练目录时遇到 root 所有的 `adapter_model.safetensors` 读取拒绝 | 只提取四份预测、报告、正式 gold 与 `run_config.json` 到本地分析，跳过本次评测不需要的权重文件 | 四组各 500 条预测与报告已收齐；没有因权重下载失败而丢失评测输入 |
| 训练时打印 `torch_dtype` 弃用提示 | 记录为非阻塞警告，训练继续使用当前已验证的依赖组合 | 三轮完成；未来升级 Transformers 时再统一迁移 `dtype` 参数并做兼容验证 |

## 5. 正式评测结果与模型选择

正式 gold 有 500 条、500 个唯一 ID，MD5 为 `27a33ffbf5d2dd01d391533cb0443f3c`。底座及 epoch 1/2/3 的四份预测各有 500 条、500 个唯一 ID，ID 集合和顺序均与 gold 一致。四份预测的原始 `text` 都能直接解析为 JSON 对象；本地使用仓库的 `pipeline/evaluate.py` 复算，指标与四份服务器 `eval_report.json` 完全一致。

| 模型 | 契约合法率 | scene 准确率 | intent 准确率 | need_cloud 准确率 | complexity MAE ↓ | 槽位微平均 F1 |
|---|---:|---:|---:|---:|---:|---:|
| 未微调底座 | 86.8%（434/500） | 37.33% | 27.88% | 49.54% | 0.4886 | 37.38% |
| epoch-1 | 100%（500/500） | 99.8% | 96.6% | 89.8% | 0.0501 | 94.97% |
| epoch-2 | 100%（500/500） | 99.0% | **97.4%** | **93.2%** | 0.0387 | 95.68% |
| epoch-3 | 100%（500/500） | 99.6% | 97.0% | **93.2%** | **0.0341** | **96.33%** |

评测脚本的 scene、intent、need_cloud 准确率以**合法输出数**为分母，因此底座的这三列只针对 434 条合法输出；三个 LoRA 模型均以 500 条为分母。底座 500 条输出都能解析为 JSON，但有 66 条违反契约，主要是 `meal` 枚举不合法（38 条）和缺少 `place_type`（26 条）。不能把“可解析 JSON”和“契约合法”混为一谈。

交接计划预设的 JSON 契约合法率 ≥98%、scene ≥92%、intent ≥88%、槽位整体 ≥90%，三个 LoRA checkpoint **均在这份教师标签评测集上**达到。分场景 scene+intent 全对率显示出取舍：epoch-2 的 reading 为 136/142（95.8%）、none 为 54/59（91.5%）；epoch-3 的 reading 为 131/142（92.3%）、none 为 58/59（98.3%）。epoch-3 在 scene、槽位 F1 和复杂度 MAE 上较好，可作为下一轮端侧验证的**候选**；若优先优化阅读意图区分，保留 epoch-2 对照。评测集已用于挑选候选模型，最终放行还需新的独立测试。

目前最明确的薄弱项是上云判断：epoch-2、epoch-3 各有 **34/500** 条与 gold 不一致。epoch-3 包括应上云却判为不上云 20 条，以及反方向 14 条；错误集中在 `none` 和 `food`，也涉及 `chat`、`location`、`reading`。此外，epoch-3 的 34 条上云错误全部输出 `confidence=0.95`。gold 中 432/500 条置信度为 0.95，模型也大量复现这个值；当前 `confidence` 不是经过校准的错误概率或可直接放行的路由阈值。

这份 gold 以教师标签为主，只有单点人工修正；500 条话语虽各不相同，上下文 `signals` 只有 8 种取值，`complexity` gold 只有 7 个离散值。高分说明模型较好复现了**当前教师数据分布与契约**，尚不能证明真实用户、陌生上下文或手机端推理的表现。正式 5500 条训练文件未随评测产物下载，本次只核对了评测内 ID 唯一及四份预测对齐，未独立复核训练/评测近重复。

下一步优先人工复核上云错误及 reading/none 边界样本，补一份覆盖新上下文和真实表述的独立测试集，再比较 epoch-2/3；同时实测端侧推理耗时、内存和契约合法率。原始预测、正式 gold 和模型权重保留在本地或训练服务器，不推送到公开仓库。
