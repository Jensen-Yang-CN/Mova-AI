# Mova-AI 城市知识库实现详解

记录时间：2026-10-29 13:47:46（北京时间）
实现范围：城市初见的资料卡片、单轮资料问答、引用展示与手机公网接入
当前资料版本：`75a26ed246dcb2ec`

## 1. 当前知识库具体做了什么

我们把公开城市资料整理成结构化文件，供「城市初见」使用。用户进入已收录城市后，可以查看当地美食、景点及推荐依据，也可以在「问问这座城」中提问。系统先找到本城相关资料，再让云模型选择资料，最终把已有摘要和来源一起展示。

本轮完成了三条链路：

1. **城市卡片**：按城市编码读取已核对的知识，展示名称、摘要、来源与核对日期。
2. **资料问答**：按城市隔离资料，运行 BM25 检索，调用云模型选择证据，返回带引用的答案。
3. **缺资料处理**：未收录城市可展示地图返回的实际店铺和景点；知识问答没有依据时明确提示资料不足。

这是一个小规模、受约束的 RAG 实现。当前采用字词检索，未接入 embedding 模型、向量数据库、重排模型、LangChain 或 LlamaIndex。资料入库没有重新训练模型，也没有修改已经微调的 0.6B 权重。

## 2. 各模块如何分工

| 模块            | 本轮承担的工作                                                         |
| --------------- | ---------------------------------------------------------------------- |
| 高德服务        | 把坐标解析成城市编码；为未收录城市检索实际地图地点                     |
| 城市资料文件    | 保存可引用的美食、景点摘要与来源，是本轮问答的事实输入                 |
| Python 检索模块 | 按城市过滤、计算 BM25、返回相关候选资料                                |
| 云端文本模型    | 阅读本次问题与候选资料，选择最多三个资料 ID；本轮联调使用 `qwen-plus`  |
| FastAPI         | 校验请求和引用，组装答案、返回 JSON、记录阶段结果                      |
| Android         | 发起请求，展示卡片、答案和可点击来源，保存城市卡片                     |
| 端侧 Qwen3-0.6B | 继续承担项目已有的结构化场景理解；当前城市知识检索和资料问答没有调用它 |

定位识别城市采用确定性地图服务，不要求语言模型猜经纬度或行政边界。云端文本模型沿用项目现有 Provider 配置，知识库模块没有单独申请一把 Key，也没有新增一份模型权重。

## 3. 资料从哪里来，怎样存储

### 3.1 当前覆盖范围

资料文件为 `scene_ai_server/knowledge/cities.jsonl`，采用 UTF-8 JSONL 格式，一行一条。

| 城市   | 行政编码 | 美食 | 景点 | 合计 |
| ------ | -------- | ---: | ---: | ---: |
| 武汉市 | `420100` |    2 |    2 |    4 |
| 岳阳市 | `430600` |    1 |    2 |    3 |
| 青岛市 | `370200` |    2 |    3 |    5 |
| 合计   | 3 座城市 |    5 |    7 |   12 |

12 条资料引用了 10 个政府网站页面。`verified_on` 均为本轮核对日期 `2026-10-29`，这个字段表示检查日期，不表示原文章在当天发布，也不表示资料会每天自动更新。

### 3.2 实际采用的整理方式

先阅读来源页面，选取与城市美食、景点直接相关且相对稳定的事实，再写成简短摘要。每条只描述一个食品或景点，保留原页面链接和标题。

本轮分块是按实体人工整理，例如「鲅鱼水饺」和「辣炒蛤蜊」分别为一块。我们没有把整篇网页存入模型上下文，也没有实现自动爬虫、长文自动切块或 PDF 批量入库。限时促销、票价、营业时间等易变化的信息没有整理进这些摘要。

### 3.3 一条真实资料的结构

```json
{
  "id": "qd-food-bayujiaozi",
  "city_code": "370200",
  "city_name": "青岛市",
  "kind": "food",
  "name": "鲅鱼水饺",
  "text": "鲅鱼水饺属于青岛常见的海鲜水饺，以鲅鱼入馅。",
  "source_title": "青岛政务网 · 在青岛的街巷里寻找舌尖上的青爽",
  "source_url": "https://www.qingdao.gov.cn/zwgk/xxgk/whly/gkml/gzxx/202512/t20251222_10415836.shtml",
  "verified_on": "2026-10-29"
}
```

| 字段                          | 用途                                       |
| ----------------------------- | ------------------------------------------ |
| `id`                          | 资料唯一标识，供云模型选择和服务端核对引用 |
| `city_code`                   | 城市隔离条件，避免检索混入其他城市         |
| `city_name`                   | 城市规范名称，也用于从问题中去除重复城市词 |
| `kind`                        | `food` 或 `sight`，供类别过滤              |
| `name`                        | 页面展示名称、地图搜索词、精确名称匹配     |
| `text`                        | 已整理的事实摘要，也是最终答案正文的来源   |
| `source_title` / `source_url` | 显示可点击的原始出处                       |
| `verified_on`                 | 记录资料编辑者的核对日期                   |

## 4. 服务端怎样加载与校验资料

入口是 `mova/city_kb.py` 的 `knowledge_base()` 和 `CityKnowledge`。

加载时检查必需字段是否为非空字符串、ID 是否重复、行政编码是否为六位数字、分类是否属于 `food/sight`、来源 URL 是否具有 HTTPS 协议与主机名、日期是否符合 `YYYY-MM-DD` 格式。同一行政编码只能对应一个城市名称。

这些是结构检查。来源是否真正支持摘要、网页是否已经迁移，需要阅读原页面和联网检查，不能仅靠 URL 格式判断。

资料文件的原始字节计算 SHA-256，取十六进制结果前 16 位作为 `kb_revision`。当前版本为 `75a26ed246dcb2ec`，用于关联卡片、问答和日志中的资料版本，不是模型权重版本。

加载对象保存在 `lru_cache(maxsize=4)` 中，缓存键包含文件路径、纳秒级修改时间与文件大小。请求时先读取文件状态，资料修改后会加载新对象。当前缓存的是解析后的资料对象；字词统计与 BM25 评分在查询时计算，没有持久化倒排索引，也没有存储向量索引。

## 5. 城市卡片与资料问答是两条路径

### 5.1 城市卡片：按城市直接取资料

Android 请求 `GET /city/guide`，服务端先查询资料库。城市已收录时，直接取出该城市资料，按美食、景点组织卡片；各类展示名称最多三个，来源按 URL 去重。卡片为 v4，并包含 `knowledge`、`knowledge_status` 与 `kb_revision`。

这条路径不执行问题检索，也不调用云模型。卡片欢迎语是固定文案；美食、景点名称与摘要来自资料文件。

未收录城市走高德地点回退：只保留本市地点，餐饮主类型须以 `05` 开头，景点主类型须以 `11` 开头；餐饮显示为店铺。地图结果不进入知识问答。完整地图结果缓存 24 小时，缓存同时检查卡片版本和 `map_cache_version=2`；部分或空结果不缓存。

### 5.2 资料问答：检索后选择证据

```mermaid
flowchart TD
    A[Android 提交城市编码和问题] --> B[FastAPI 请求校验]
    B --> C{城市已收录且属于静态资料范围?}
    C -- 否 --> D[返回资料不足提示]
    C -- 是 --> E[按城市过滤资料]
    E --> F[类别判断与中文 n-gram BM25]
    F --> G{是否有命中?}
    G -- 否 --> D
    G -- 是 --> H[最多4块候选资料送云模型]`
    H --> I[模型返回最多3个资料 ID]
    I --> J[服务端核对引用白名单]
    J --> K[用已有摘要组成答案和引用]
    J -- 空选择 --> D
    H -- 超时或格式异常 --> L[展示检索到的原资料]
```

`POST /city/ask` 的请求要求城市编码为六位数字，问题长度为 2–300 字符。未收录城市直接返回资料不足；涉及票价、营业、天气、路线、预约、今天、现在等关键词的问题，先由静态范围规则拦截。

范围判断采用关键词规则，存在保守拒答的情况，例如问题含有「现在」也可能被拦截。它没有实现通用的实时问题语义分类。

## 6. BM25 检索具体怎么算

### 6.1 先按城市和类别缩小候选

先用 `city_code` 过滤。青岛问题只会在青岛的五块资料中检索，不会把武汉热干面送给模型。城市名称从查询文本中去除，避免每块资料都因为带有城市名而被认为相关。

问题包含「美食、小吃、吃、味道、菜、早餐」等词时识别为美食方向；包含「景点、逛、玩、游览、风景、地标」等词时识别为景点方向。只有一个方向命中时按该分类过滤；两个方向同时命中或都未命中时保留本城各类资料。

### 6.2 中文字词处理

对名称和摘要拼接后的文本做统计。中文提取单字与相邻双字片段，英文和数字按连续词处理并转为小写。例如「八大关」得到「八、大、关、八大、大关」。查询另外去掉「请问、有哪些、有什么、推荐」等常见提问词和部分虚词。

本轮使用代码中的 n-gram 规则，没有调用 jieba 或分词模型。检索比较的是字词重合，尚不具备 embedding 的语义召回能力。

### 6.3 评分与截断

BM25 参数为 `k1=1.2`、`b=0.75`，公式与实现对应如下：

```text
IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))

BM25 = Σ IDF(t) × f(t,d) × (k1+1)
         / [f(t,d) + k1 × (1-b + b × length(d)/avg_length)]

最终分数 = BM25
           + 3（问题具有单一美食或景点方向）
           + 8（问题中包含该资料的完整名称）
```

`N` 与 `df` 在本城资料集合内计算，文本长度为提取的字词片段总数。查询按出现过的不同片段求分，没有额外叠加查询词频权重。

无类别提示、无完整名称时，要求至少命中一个长度不小于 2 的片段，避免「市长是谁」仅因一个「市」字匹配到旅游资料。保留最终分数大于 `0.05` 的候选，按分数降序、ID 升序稳定排序，默认最多返回四块。

上述加分与阈值是首版实现参数，不是训练得到的概率，也没有经过大规模参数寻优。

## 7. 云模型怎样参与，答案怎样得到

### 7.1 模型只选择候选证据

云模型输入包含本次问题，以及命中资料的 `id/name/text`。提示要求模型选择直接相关的 ID，最多三个，资料不足时返回空列表；问题与资料中的指令按数据处理。

模型响应契约为：

```json
{ "ids": ["qd-food-geli", "qd-food-bayujiaozi"] }
```

服务端验证响应为列表、数量不超过三、每项为字符串、每个 ID 均属于本次检索候选，再按 ID 去重。模型不能通过返回结果新增名称、摘要或来源链接。城市问答使用现有 `CITY_PROVIDER`：本轮调用温度为 0，上游请求超时 10 秒、重试次数 0。

### 7.2 正文由服务端组装

通过校验后，服务端取选中资料的既有摘要，按「名称：摘要 [编号]」组织答案。当前没有让模型自由改写整段正文，也没有开放跨资料推理、多轮记忆或联网搜索。

例如青岛美食问题返回：

```text
辣炒蛤蜊：辣炒蛤蜊是青岛地方美食介绍中的常见菜肴，风味以鲜辣为主。 [1]

鲅鱼水饺：鲅鱼水饺属于青岛常见的海鲜水饺，以鲅鱼入馅。 [2]
```

这里的编号对应资料块。两块资料引用同一网页时，两个编号的来源 URL 可以相同。来源链接取自本地资料，模型不负责生成链接。

这种限制减少了无依据扩写的空间，但资料编辑错误、检索相关性不足、来源后来失效仍会影响结果；不能把结构约束等同于事实永远正确。

### 7.3 三种响应状态

| `mode`         | 何时出现                                         | 用户得到什么                             |
| -------------- | ------------------------------------------------ | ---------------------------------------- |
| `rag`          | 模型返回了通过校验的证据 ID                      | 已选摘要与对应引用                       |
| `retrieval`    | 未调用模型，或模型异常、格式／引用不合法         | 默认最多前三块检索资料；页面标为相关资料 |
| `insufficient` | 未收录、超出静态范围、无命中或模型有效返回空列表 | 无引用的资料不足提示                     |

`grounded=true` 表示结果引用了资料库中的内容，不代表已测得某个准确率。响应还返回 `retrieved_count`、`kb_revision`、`latency_ms`。日志记录城市编码、命中数、引用数、模式、耗时和版本；知识库日志不记录问题全文、坐标或 Key。

## 8. Android 如何调用与展示

1. `CityScreen.kt` 提供「看看推荐依据」「问问这座城」和两条快捷问题。
2. `CityTripManager.askCity()` 去除问题两端空白，最多保留 300 字符，并阻止同城重复提交。
3. `MovaApi.askCity()` 通过 Retrofit 向 `/city/ask` 发送城市编码与本次问题，手机侧等待上限为 20 秒。
4. `CityAnswer` 与 `CityKnowledgeItem` 解码结果。页面显示回答，并由用户点击后打开来源网页。
5. 请求失败时显示错误并恢复操作。单轮答案保存在管理器内存中；城市卡片另外保存到本机 SharedPreferences，最近保留 20 条，包含资料和模拟标记。

旧卡片版本小于 v4 时会请求刷新；刷新同一城市会更新该城市已保存的卡片并保留到达时间。v4 中明确标记为资料未收录的卡片不会因空内容而在每次打开时反复请求。

用户可以离线查看已经保存的城市资料，新的问答仍需要连接后端。资料库更新后，已存手机卡片属于旧快照，可点击「刷新城市推荐」获取新内容；当前没有按 `kb_revision` 自动推送卡片更新。

设置页的忌口目前用于菜谱请求，城市知识库没有自动读取它来筛选推荐。本轮问答只发送城市编码和本次问题，不发送精确位置、完整行程或其他聊天历史。

## 9. 公网服务与构建配置

当前实际链路如下，私有域名在文档中用 `xxx` 表示：

```text
Android 移动网络
    → https://xxx.ts.net/api/
    → Tailscale Funnel
    → 电脑本地 8080 端口的 FastAPI
    → 本地资料检索 + 云端文本模型证据选择
```

Funnel 根路径保留安装包下载，`/api/` 单独转发后端。FastAPI 当前仍运行在开发电脑上；没有部署独立云主机，电脑与隧道需要持续在线。

更新时发现手机仍保存本地地址，原因是之前的调试构建未注入公网默认值。已给 Gradle 增加地址配置回退，优先级为命令行参数、`MOVA_SERVICE_BASE_URL` 环境变量、已忽略的 `local.properties` 内的 `mova.serviceBaseUrl`。配置公网默认值后，旧本地地址会显示为公网地址；手机已点击「保存并检测」保存新地址。

实际公网地址和模型 Key 不写入本工作文档。模型 Key 仅在服务端配置；Android 构建只注入 Mova 后端地址。

同步到其他服务环境时，需要一起部署 `app.py`、`mova/cities.py`、`mova/city_kb.py` 和整个 `knowledge/` 目录，再重启 FastAPI。Dockerfile 已包含资料目录。手机安装更新后的 APK，刷新已有卡片，分别检查推荐依据、正常问答与资料不足提示。

## 12. 如何检查和继续维护

在主仓库根目录执行：

```powershell
# 校验结构，打印覆盖范围、来源数量和资料版本
python tools/city_kb.py

# 仅做本机检索，不调用云模型
python tools/city_kb.py --city-code 370200 --question "当地有哪些特色美食"

# 联网检查来源 HTTP 状态、标题和错误类型
python tools/city_kb.py --check-sources

# 运行后端相关回归测试
Push-Location scene_ai_server
python -m unittest discover -s tests -p 'test_cit*.py' -v
Pop-Location
```

复跑手机测试时，先使用 `tools/run_android.ps1` 中的 Android 环境配置，构建 `:app:assembleDebugAndroidTest` 并安装生成的测试 APK，再运行：

```powershell
adb shell am instrument -w -r -e class com.mova.sceneai.data.city.CityRagDeviceTest com.mova.sceneai.test/androidx.test.runner.AndroidJUnitRunner
```

完整用例报告需出现 `OK (2 tests)`，不能只看命令退出码。测试沿用手机当前服务地址，并保存一张标注为模拟行程的青岛卡片；要验证公网，运行前须确认已移除 ADB reverse，且手机使用移动网络。

补充新城市时，先核实六位行政编码，阅读可信来源，把食品或景点分别写成独立 JSONL 行，使用新 ID，并填写实际核对日期。运行结构和检索检查后，同步资料文件到正在运行的服务端；服务器通过文件状态重新加载。手机手动刷新对应卡片，再检查引用与原文是否一致。新增资料无需重训端侧或云端模型。

链接检查只检查当前连接结果和页面标题，不能自动证明正文支持摘要。TLS、超时也不能直接等同于网页已删除，需结合手机浏览器再次确认。

## 13. 当前边界与后续工作

当前只覆盖 3 座城市的 12 条事实，不能回答全国城市的任意问题。字词召回依赖表述重合，单条摘要也难以回答详细历史、路线规划或复杂比较。单轮问题没有前文记忆，关键词范围限制有保守拒答，事实正确性仍依赖资料整理与维护。

本轮没有做向量检索、自动网页同步、RAG 专项大规模准确率评测、真实铁路跨城测试或长期后台稳定性测试。现有 500 条教师标签评测与 150 条压力题针对此前的端侧场景模型，不能用来充当知识库问答准确率。

- [ ] 根据实际演示与用户问题补充城市和事实，保持每条来源可核查。
- [ ] 检查弱网、超时后的页面恢复体验。
- [ ] 出现明确的同义表达漏召回后，再评估 embedding、混合检索与重排。
- [ ] 如需长期对外服务，将 FastAPI 迁移到独立云部署环境。

当前实现可以准确概括为：**把有来源的城市事实按实体整理入库，先按城市和类别过滤，再进行 BM25 检索；云模型选择候选证据 ID，服务端核对后用已有摘要形成答案，Android 同屏展示可点击引用。**
