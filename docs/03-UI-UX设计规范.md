# Mova-AI UI/UX 设计规范

> 本文定义界面的信息架构、页面规格、组件与文案规范。核心理念：**新用户不需要读文档，也不需要配 Key。**

---

## 1. 设计目标：把"新用户友好"拆成可验收的条目

"友好"不能只是感觉，必须可检查。本项目的验收标准：

| # | 标准 | 具体做法 |
|---|---|---|
| 1 | 首启最多 3 步进入主界面 | 3 屏向导，每屏一个动作 |
| 2 | 用户不需要自己想"输入什么" | 每个能力页提供**一键示例** |
| 3 | 每个空状态都有明确的下一步 | 空状态 = 插图 + 一句话 + 一个按钮 |
| 4 | 每个错误都能自己解决 | 中文原因 + **可点击的解决办法** |
| 5 | 每个结果都能拿走 | 所有结果卡都有复制按钮 |
| 6 | 每个权限都有理由 | 授权前用一句话说明"用来做什么" |
| 7 | 长内容不被截断 | 严禁用 Toast 承载结果，一律结构化卡片 |
| 8 | 高级能力不吓人 | 技术面板/路由信息放二级页，主流程零术语 |

---

## 2. 信息架构

```
首次启动
   └── 首启向导（3 屏）
         ├─ ① 价值说明
         ├─ ② 权限说明与授权
         └─ ③ 连接配置（含"检测连接"与演示模式兜底）

主界面（底部导航 4 个 tab）
   ├── 🏠 首页 Home
   │      ├── 连接状态卡
   │      ├── 主动智能总开关
   │      ├── 场景能力网格 ──▶ 二级页面
   │      │       ├── 做饭 Food
   │      │       ├── 阅读 Reading（文本 / 图片 / PDF 三 tab）
   │      │       └── 聊天 Chat
   │      └── 今日概览（调用次数 / 端云占比）
   ├── 🕘 记录 History ──▶ 结果详情
   ├── 📊 技术面板 Tech
   └── ⚙️ 设置 Settings
```

**为什么技术面板要独立成一个 tab？** 因为它同时服务两类人：用户看到"AI 做了什么决定"，面试官看到"这个项目有什么技术含量"。放在设置深处等于藏起来。

## 3. 页面规格

### 3.1 首启向导

**屏 1 · 价值说明**
- 大标题：**不用开口，它自己知道**
- 副标题：Mova-AI 感知你正在做什么，在最合适的时刻主动帮忙
- 三张场景小卡（非交互，纯展示）：🍜 在厨房举起手机 → 直接给菜谱｜📄 看到长文 → 自动摘要｜💬 不知道怎么回 → 给推荐话术
- 按钮：`开始使用` / 文字按钮 `跳过`

**屏 2 · 权限说明**
| 权限 | 用途说明（必须出现） |
|---|---|
| 相机 | 拍食材、拍文章，用于识别内容 |
| 通知 | 场景触发时提醒你（可随时关闭） |

每行：图标 + 名称 + 一句用途 + 右侧 `授权` 按钮；未授权时点击触发系统弹窗；已授权显示 ✅。
底部文字按钮 `稍后再说`（**允许跳过**，不阻塞主流程）。

**屏 3 · 连接配置**
- 说明：Mova-AI 的重推理需要连接你的 AI 服务；即使不连，端侧能力也可用（端侧就绪后）
- 输入框：服务地址（默认 `http://10.0.2.2:8000/`，附说明"模拟器用 10.0.2.2；真机填电脑局域网 IP"）
- 按钮：`检测连接` → 显示结果：
  - ✅ `已连接 · qwen3-max` + 延迟
  - ❌ `无法连接` + 排查清单（地址对不对 / 服务是否启动 / 手机与电脑是否同一 WiFi）
- 按钮：`完成`；文字按钮 `先用演示模式`（跳过检测，直接进主界面）

状态卡三种形态（**颜色语义必须一致**）：

| 状态 | 颜色 | 文案 |
|---|---|---|
| 云端可用 | 绿 | `云端已连接 · <模型名>` + 延迟 |
| 云端不可用、端侧就绪 | 蓝 | `端侧模型运行中 · 离线可用` |
| 都不可用 | 橙 | `无法连接服务` + `去设置` 按钮 |

### 3.3 做饭 Food

- **引导条**：`拍一张食材照片，剩下的交给我`
- **三个输入入口**（大按钮，等权）：
  - `📷 拍照识别`（调用系统相机，**全分辨率**输出）
  - `🖼 从相册选择`
  - `✨ 试试示例`（内置示例图，冷启动友好——新用户第一件事就能看到结果）
- **处理中**：不使用转圈，使用**阶段化骨架屏**：
  - 阶段 1：`正在识别食材…`（对应后端视觉模型）
  - 阶段 2：`正在生成做法…`（对应后端语言模型）
  - 这个设计同时把"两级流水线"这个技术点传达给了用户
- **结果卡**：
  - 菜名（大标题）
  - 食材 chips
  - 步骤列表（序号 + 文本，多行不截断）
  - 小贴士（带 💡 的独立卡片）
  - 底部操作：`复制全部`｜`再拍一张`

### 3.4 阅读 Reading

- Tab：`文本` / `图片` / `PDF`
- 文本：多行输入 + 实时字数
- 图片：拍照 / 相册
- PDF：系统文件选择器（`ACTION_OPEN_DOCUMENT`，MIME `application/pdf`）
- 结果卡（三种输入共用，**出口契约一致**）：
  - 摘要段落
  - 要点列表（≤5 条）
  - 难度徽标（简单 / 中等 / 偏难，颜色区分）
  - 追问建议：一条可点击的建议问题 → 点击后直接发起追问并展示回答

### 3.5 聊天辅助 Chat

- 输入：`对方说了什么？`
- **风格 chips**（单选）：自然 / 礼貌 / 委婉 / 幽默 / 职场 / 亲密 / 冷处理
- **目标 chips**（单选）：不指定 / 接受 / 拒绝 / 推迟 / 转移话题 / 降低冲突
- 可展开的「多轮上下文」：添加多条 `我/对方` 消息
- 结果区（**三段式，与"人机协作"的产品立场一致**）：
  1. 推荐回复（高亮卡片 + `复制`）
  2. 备选回复（列表，每条可单独复制）
  3. `为什么这样回`（可折叠的解释区）
- 底部：`换一批`

> 结果区刻意做成"给人选择而不是替人做决定"——这是产品立场，也正好是 AI 沟通辅助与传统 ChatBot 的分界。

#### 输入来源：系统分享入口（`ACTION_SEND`）

聊天页还有一个**从外部进来的入口**：用户在微信里长按对方的消息 → 分享 → Mova-AI。
内容会作为 `EXTRA_TEXT` 进来，自动填入输入框并立刻生成建议。

```
微信长按消息 → 分享 → Mova-AI
      ↓
MainActivity.onNewIntent（launchMode=singleTask，复用实例）
      ↓
SharedInbox.post(text)          ← Activity 只负责"接住"
      ↓
MovaRoot 观察到有待处理内容 → 导航到聊天页
      ↓
ChatViewModel.init → SharedInbox.take() → 填入 + 自动生成
```

界面上的三条约束：

1. 页面顶部有绿色提示条：**「来自分享：内容已填入下方…这是你主动分享的，App 不会读取其它应用的界面。」**
   必须让用户清楚数据是怎么来的 —— 这是隐私透明度的基本要求
2. 用户一旦手动编辑输入框，提示条消失（不再强调来源）
3. 首启向导未完成时不跳转，避免用户被直接扔进聊天页而错过权限与连接配置

##### 为什么不做无障碍读屏（一个明确的技术决策）

`AccessibilityService` 能自动感知"你正在用微信"并读取屏上的对话，不需要用户手动分享。
这个方案**技术上可行**，但被主动放弃，理由有三条：

| 约束 | 说明 |
|---|---|
| **微信服务协议** | 明确禁止自动化读取与操作，账号有被限制功能的风险。这不是 Android 权限问题 —— Android 会放行，但微信侧不允许 |
| **Android 13+ 的限制** | 侧载应用默认**禁止**开启无障碍服务，用户必须先在「应用信息 → 受限设置」里手动解除。这个摩擦是 Google 有意加的，就是为了防止侧载应用滥用无障碍 |
| **个人信息合规** | 读到的是**对方**发来的消息，属于第三方个人信息；上传云端大模型构成对外提供。这在《个人信息保护法》下是高压线 |

分享入口在合规、可靠性、成本三项上都更优，代价只是用户多一次点击。
**把这个取舍写进文档本身就是交付物的一部分** —— 它证明的是工程判断力，而不只是编码能力。

### 3.6 记录 History

- 顶部过滤 chips：全部 / 做饭 / 阅读 / 聊天
- 列表项：场景图标 + 标题摘要 + 相对时间 + 执行器徽标（端侧 / 云端）
- 点击 → 结果详情页（复用结果组件）
- 空状态：`还没有记录` + `去试试做饭助手` 按钮

### 3.7 技术面板 Tech

这是本项目的"技术透明层"，也是对面试官的自证材料。

- **会话总览**：端侧 N 次 · 云端 M 次 · 降级 K 次 · 云端占比 P%
- **最近请求列表**，每行：
  `时间` | `场景` | `执行器徽标` | `耗时` | `置信度` | `路由原因`
  例：`14:32 · 做饭 · 云端 · 1.24s · 0.71 · 端侧槽位校验未通过`
- **延迟拆解**：横向条形（预处理 / 推理 / 后处理）
- **端侧模型卡**：模型名、文件大小、量化位宽、加载耗时；
  未就绪时显示 `端侧模型未部署` + 说明（**不要假装有**）
- **导出日志**按钮
- 页首说明文案：一句话解释这个面板在展示什么

### 3.8 设置 Settings

| 分组 | 项 |
|---|---|
| 服务连接 | 地址（可编辑）、`检测连接`、超时设置 |
| 主动智能 | 总开关、免打扰时段、打扰敏感度（低/中/高） |
| 端侧模型 | 状态、`优先使用端侧`（未就绪时禁用并说明） |
| 外观 | 跟随系统 / 浅色 / 深色 |
| 数据 | 清除历史记录、重新运行首启向导 |
| 关于 | 版本号、项目说明、开源许可 |

## 4. 设计 Token

| 项 | 取值 |
|---|---|
| 主色 | 紫蓝系（AI 感），Material 3 `colorScheme` |
| 语义色 | 成功 = 绿；提示/降级 = 橙；错误 = 红；端侧 = 蓝 |
| 卡片圆角 | 20 dp |
| 按钮圆角 | 16 dp |
| Chip | 全圆角 |
| 间距刻度 | 4 / 8 / 12 / 16 / 24 dp |
| 字体 | 标题 `titleLarge`；正文 `bodyMedium`；说明 `bodySmall` + `onSurfaceVariant` |
| 深色模式 | 完整支持，跟随系统 |
| 边缘适配 | `enableEdgeToEdge()` + Scaffold insets，避免状态栏遮挡 |

## 5. 文案规范

1. **说人话**：不出现 `API`、`token`、`prompt`、`endpoint` 等术语（技术面板除外）
2. **错误必须三件套**：发生了什么 + 为什么 + 怎么办
   - ✅ `无法连接服务。可能是手机和电脑不在同一个 WiFi。` + `[ 去设置 ]`
   - ❌ `NetworkError: connect failed (ECONNREFUSED)`
3. **不指责用户**：`地址好像填错了` 而不是 `输入无效`
4. **主动提供兜底**：错误信息下永远存在一个可点的出路（重试 / 去设置 / 用示例）

## 6. 状态与反馈

| 状态 | 表现 |
|---|---|
| 加载 | 骨架屏 + 阶段文案（能对应后端真实阶段） |
| 成功 | 结果卡 + 可复制 |
| 空 | 插图 + 引导文案 + 主行动按钮 |
| 失败 | 三件套文案 + 出路按钮 |
| 降级 | 顶部细横幅：`端侧资源繁忙，本次已切换云端` |
| 首次进入某页 | 一次性提示条（可关闭，记录已读） |

---

## 7. 端侧就绪前后的界面行为

界面必须**诚实地反映端侧模型的真实状态**，不允许假装已有端侧能力（这是诚信问题，也会在面试中被追问穿）。

| 端侧状态 | 界面表现 |
|---|---|
| 未部署 | 技术面板显示 `端侧模型未部署`；设置里 `优先使用端侧` 禁用并附说明 |
| 已部署未加载 | 显示 `加载中…` 与文件大小 |
| 已就绪 | 状态卡出现 `端侧可用`；路由统计开始区分端/云 |

这样设计的好处：端侧模型接进来时，界面**不需要改动**，只是从"未部署"变成"已就绪"，指标自然点亮。
