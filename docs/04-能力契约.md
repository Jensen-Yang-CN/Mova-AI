# Mova-AI 能力契约（S1）

> 本文说明端侧小模型**到底要学什么**，以及这份契约为什么是**可执行的**而不是纸面的。
> 契约的权威定义在代码里：[`scene_ai_server/pipeline/contract.py`](../scene_ai_server/pipeline/contract.py)。

---

## 1. 为什么先做契约

端侧蒸馏最容易走偏的路径是：直接拿教师模型生成一堆"问答对"，训出来的学生什么都会一点、什么都不精，接进系统后表现出"判断不可靠"，最终所有请求还是上云 —— **项目退化成一次调 API**。

所以第一件事不是选模型，而是**划定能力边界**。

### 三条边界原则

| 原则 | 含义 |
|---|---|
| **面向决策，不面向创作** | 端侧只输出"判断"（场景、意图、复杂度、是否上云）与"抽取"（结构化槽位），不输出长文本 |
| **高频、短输出、可校验** | 只有满足这三条的能力才放端侧；否则放端侧只是徒增失败率 |
| **错误可被发现** | 端侧输出的每一条都能被外部校验（枚举合法性、槽位必填、JSON Schema），校验不过就升级云端 |

## 2. 契约内容

### 2.1 输出结构

```jsonc
{
  "scene": "food | reading | chat | location | none",
  "intent": "diet_advice | summarize | reply_suggest | ...",   // 与 scene 强绑定
  "complexity": 0.42,        // [0,1]，衡量"是否需要长推理或长生成"
  "confidence": 0.91,        // [0,1]，模型自报把握（后续还需外部校准）
  "need_cloud": true,        // 布尔，是否应该上云
  "slots": { "ingredients": ["番茄", "鸡蛋"] },
  "reason": "不足 60 字的判断依据"
}
```

### 2.2 为什么让模型自己输出 `need_cloud`

这是整份契约里最关键的一个设计决定。

对比两种做法：

| 做法 | 路由依据 | 问题 |
|---|---|---|
| 端侧只做分类，路由由外部规则决定 | `if (复杂度 > 0.7) 上云` | 规则是拍脑袋的，没有依据，也无法被训练改进 |
| **端侧直接输出 `need_cloud`** | 模型学到的判断 | **路由成为一项被蒸馏出来的能力** |

后者带来三个直接好处：

1. 教师在生成训练数据时，会对每条样本给出它认为正确的 `need_cloud`，学生学的就是这个判断 —— 于是"什么时候上云"这件事是**从云端大模型迁移过来的**，而不是人写的阈值
2. 路由决策因此可以被评测（见 `pipeline/evaluate.py` 的 `need_cloud_accuracy`）
3. 端侧模型升级（0.6B → 1.7B）时，路由行为会自动变好，不需要改代码

### 2.3 槽位设计

槽位按 `scene` 分支，每个槽位声明**类型、是否必填、取值范围**：

| 场景 | 槽位 |
|---|---|
| `food` | `ingredients`（字符串数组，必填）、`meal`（枚举，可选） |
| `reading` | `text_length`（整数，必填）、`source`（枚举，必填）、`topic`（字符串，可选） |
| `chat` | `target_tone`（枚举，必填）、`goal`（枚举，必填）、`relation`（枚举，可选） |
| `location` | `place_type`（枚举，必填）、`time_bucket`（枚举，可选） |

## 3. 契约是可执行的

`contract.py` 提供三样东西，全部被流水线真实调用：

| 能力 | 函数 | 被谁用 |
|---|---|---|
| **JSON Schema** | `json_schema()` | 产出 `data/edge_contract.schema.json`，端侧推理时交给语法约束解码（GBNF / JSON-Schema） |
| **校验器** | `validate(obj) -> list[str]` | 数据流水线判定教师样本是否合格；评测算"契约合法率" |
| **任务提示** | `contract_prompt(signals, utterance)` | 离线蒸馏与在线服务**共用同一份**定义 |

最后一条尤其重要：**教师看到的任务描述，与未来端侧模型要面对的任务完全一致**。如果两边 prompt 不一致，学生会学到与部署环境不匹配的分布 —— 这是蒸馏里最常见的隐性坑。

### 语法约束解码为什么值得做

端侧小模型最大的工程问题不是"答得不好"，而是**格式崩坏**：自由解码下 JSON 合法率可能只有六七成。用 Schema 约束解码后，采样过程只能在合法 token 上走，合法率直接到 100%，且不需要重试。

契约里的枚举被刻意设计得**紧凑且互斥**，就是为了让约束解码的搜索空间足够小 —— 约束太宽会拖慢解码。

## 4. 第一次实测暴露的两个缺陷（真实记录）

契约不是一次写对的。这两个问题都是**跑起来才发现的**，记录下来比假装一次做对更有价值。

### 缺陷一：枚举用了英文，且 prompt 没列取值

第一版 `food.meal` 的枚举是 `breakfast / lunch / dinner / snack`，而 `contract_prompt` **只列出了槽位名，没有列出允许取值**。教师只能猜，于是输出「晚饭」「午饭」。

**实测结果：契约合法率 0%（0/8）。**

两处修正：

1. `meal` 改用领域里的自然中文（`早饭 / 午饭 / 晚饭 / 夜宵`），与种子词表一致
2. `contract_prompt` 改为**逐条列出每个槽位的类型与全部允许取值**，并追加一句"必须逐字照抄，不要翻译、不要同义词"

修正后同一条流水线：**契约合法率 100%（8/8）**。

> 教训：**契约必须显式到模型能照抄的程度。** "模型应该能理解"是一种假设，不是工程。

### 缺陷二：用平均对数概率衡量置信度，几乎没有区分度

信号二原本取 `exp(mean_logprob)`。但契约输出是 JSON，大量 token 是 `{`、`"`、`scene` 这类高度可预测的结构符号，对数概率接近 0，把均值抬得很高且几乎不随样本变化。

**实测结果：8 条样本的难度全部落进 "easy" 档，平均难度 0.151。该信号完全没有区分度。**

修正：改用 **10 分位对数概率**（教师"最没把握的那几处"有多没把握），这才对应我们真正关心的东西 —— 这个任务的判断边界清不清晰。

> 教训：**指标要检查它的方差，而不只是它的值。** 一个所有样本都取同一个值的"信号"等于没有这个信号。

## 5. 契约与下游的接口

| 下游环节 | 用到契约的什么 |
|---|---|
| 数据引擎 | `contract_prompt` 构造教师任务；`validate` 判定合格率 |
| 覆盖度优化 | 网格定义 = `scene × intent × 难度档 × 槽位组合` |
| 配比求解 | 难度档来自 `complexity`（或实测难度） |
| 量化后的端侧推理 | `json_schema()` 交给语法约束解码 |
| 端云路由 | `need_cloud` + `confidence`（校准后）作为决策输入 |
| 评测 | `validate` 算合法率；槽位比对算 P/R/F1 |
