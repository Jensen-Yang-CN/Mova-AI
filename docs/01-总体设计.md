# Mova-AI 总体设计

> 本文是项目的**技术总纲**：定义问题、给出统一算法框架、划分模块、说明创新点与实验设计。
> 端侧模型的训练与部署细节见 [`02-端侧模型方案.md`](02-端侧模型方案.md)，界面规范见 [`03-UI-UX设计规范.md`](03-UI-UX设计规范.md)。

## 0. 一句话定位

> **Mova-AI 是一个把「云端大模型的场景理解能力」蒸馏进端侧小模型、并基于校准置信度做端云级联推理的移动智能助手。**

它要回答的不是"怎么调用一个大模型"，而是移动端 AI 的三个真问题：

| 真问题 | Mova-AI 的回答 |
|---|---|
| 什么时候该出现？ | 把"要不要打扰用户"建模成带代价的序列决策，用上下文老虎机在线学习 |
| 端侧模型能扛多少？ | 定义**能力契约**：端侧只学场景理解—意图判定—难度评估—结构化抽取，重推理上云 |
| 什么时候必须上云？ | 把路由写成**代价敏感决策**：比较端侧校准置信度与云端延迟/费用/隐私代价 |

### 为什么这套定位对标 OPPO 小布 / 小米小爱

这两家厂商的竞争壁垒恰好就在这三件事上：端侧模型（[OPPO AndesGPT](https://tech.ifeng.com/c/8umZSC9ocSg?ch=ttsearch)、[小米 MiLM](https://jiweipreview.laoyaoba.com/n/904375) 均已通过备案）、主动智能（[OPPO 官方目标即"更个性化的主动智能体验"](https://www.ithome.com/0/977/218.htm)）、端云协同推理。因此本项目的每一层都刻意对齐这三点，而不是做成一个"套壳对话框"。

## 1. 问题定义：从工具型 AI 到主动智能

现有实现的本质是 *"用户提问 → 云端大模型 → 返回结果"*。这条链路的三个结构性缺陷：

1. **触发靠人**：用户必须先意识到"这儿可以用 AI"，再打开 App、组织语言。认知成本高。
2. **无端侧能力**：断网即废，延迟受 RTT 支配，且每一次交互都要把数据送出设备。
3. **不可解释**：用户不知道 AI 为什么出现，也无法预测它下次会不会又跳出来。

Mova-AI 把这条链路重构成：

```
环境信号 ──▶ ①要不要出现 ──▶ ②用什么模型 ──▶ ③结果怎么呈现 ──▶ ④用户反馈
             (触发决策)      (级联路由)       (结构化渲染)     (在线学习)
                  ▲                                              │
                  └──────────────────────────────────────────────┘
```

关键在于 ① 和 ② 都由**模型**给出，而不是写死的规则或阈值。

## 2. 核心框架：代价敏感级联路由

整个项目收敛到**一个**统一框架，而不是四套互不相干的 if-else。

### 2.1 形式化

对一次感知→执行的请求，系统有一组候选执行器 $\{M_1, M_2, \dots, M_n\}$（例如：端侧 0.5B → 端侧 1.7B → 云端大模型），每个执行器 $M_i$ 有：

- $p_i$：该执行器在当前任务上给出可接受结果的概率（**必须经过校准**，见 §6.3）
- $L_i$：端到端延迟（含预处理、推理、后处理）
- $C_i$：代价（云端 token 费用、隐私暴露风险、电量）

系统选择 $M_k$ 使期望效用最大：

$$
k = \arg\max_i \Big[\, p_i \cdot V(\text{task}) \;-\; \lambda L_i \;-\; \mu C_i \,\Big]
$$

工程上取一个更直白的等价形式（**级联**：从小到大试，够了就停）：

$$
\text{停在 } M_i \iff p_i \;\ge\; p_{\text{cloud}} - \lambda\,(L_{\text{cloud}} - L_i) - \mu C_i
$$

$\lambda, \mu$ 由**实测标定**（见 §7 实验设计），不是拍脑袋的常数。这条式子的实际含义是：*端侧模型每次省下的毫秒和隐私，正好可以"买"多少精度损失*。

### 2.2 两个层级，同一个框架

| 层级 | 执行器序列 | 置信度来源 |
|---|---|---|
| **视觉级联** | 端侧轻量分类器（MobileNetV3 / EfficientNet-Lite，5–20 MB）→ 云端多模态大模型 | 分类器 softmax + 温度缩放校准 |
| **语言级联** | 端侧 SLM（Qwen3-0.6B / 1.7B，INT4）→ 云端大模型 | token 级对数概率聚合 + 温度缩放校准 |

**这就是本项目最重要的设计决策**：视觉和语言不做成两套逻辑，而是同一套级联路由的两个实例。这让整个系统只有一个需要调参、一个需要评测、一个需要解释的决策点。

### 2.3 兜底：任务级投机执行

级联的"升级"判断不只看置信度，还看**结构合法性**：

- 端侧用**语法约束解码**（GBNF / JSON Schema 约束）保证输出一定是合法 JSON
- 解析后跑一遍**槽位校验**（必填字段、枚举取值、数值范围）
- 校验失败 → **不重试端侧**，直接升级云端

这样端侧小模型"JSON 格式崩了"这个最常见的失败模式被结构性消除，而不是靠 prompt 祈祷。这也让端云切换的原因可解释（"端侧槽位校验未通过"），可以直接展示给用户。

### 3.1 一条设计原则：`Executor` 接口统一

端侧与云侧**实现同一个接口**：

```kotlin
interface Executor {
    val id: String                 // "edge-qwen3-0.6b-int4" / "cloud-qwen3-max"
    suspend fun infer(req: MovaRequest): MovaResponse
}
```

路由层不关心谁是本地谁是远程。好处：

1. 加一个新执行器（例如 NPU 加速版）不改路由代码
2. **评测时可以把云端执行器换成 mock**，在没有网络的情况下跑完整的路由消融实验
3. 端侧模型还没训好时，用同一个接口挂一个"永远失败"的桩，就能先验证路由与降级逻辑

## 4. 技术选型

### 4.1 端侧（Android）

| 项 | 选型 | 理由 |
|---|---|---|
| 语言 | **Kotlin** | 协程 + 密封类，适合表达"加载中/成功/失败/降级"这类状态 |
| UI | **Jetpack Compose + Material 3** | 声明式，多页面 + 动态状态（加载/流式/降级）代码量远低于 XML |
| 导航 | **Navigation Compose** | 页面即函数，路由集中声明 |
| 状态 | **ViewModel + StateFlow** | 单向数据流，UI 只渲染 `UiState` |

| 本地设置 | **DataStore(Preferences)** | 替代 SharedPreferences，支持协程/Flow |
| 图片 | **Coil** | Compose 原生集成 |
| 端侧推理 | **llama.cpp（GGUF）主线 / LiteRT-LM 对照** | llama.cpp 量化格式最全、可控性最强；LiteRT-LM 零 NDK 门槛，用于横评 |
| NPU 加速 | **QNN（ExecuTorch / ONNX Runtime QNN EP）** | 目标机 OPPO Find X7 Ultra = 骁龙 8 Gen 3，Hexagon NPU 可用，是冲刺项 |

## 6. 创新点

每个创新点都对应**一个可量化的指标**，避免"看起来很高端但没法验证"。

### 6.1 统一级联路由框架（端 + 云 + 视觉 + 语言）

把端云协同、视觉多级、语言多级统一成同一个代价敏感决策问题（§2）。相比"按规则判断上不上云"的做法，优点是可标定、可评测、可解释——每次决策都能回答"为什么这次走了云"。

> **指标**：云端调用占比 ↓、P95 延迟 ↓、任务准确率不显著下降

### 6.2 校准置信度驱动的升级判据

直接用 softmax 概率做阈值是错的：小模型普遍**过度自信**。用温度缩放/等渗回归做后验校准，以 ECE（Expected Calibration Error）为指标。

> **指标**：ECE 从 __ 降到 __；路由的误判率（该上云没上云）↓

### 6.3 任务级投机执行

端侧先做，用语法约束解码 + 槽位校验判断结果是否可用，不可用才上云 —— 相当于把投机解码的思想从 token 级提升到任务级。

> **指标**：端侧结构化输出合法率 → 100%；云端调用量 ↓ __%

### 6.4 三信号客观难度评估

不依赖模型自评（自评校准差），改用三个客观信号合成难度：

1. **教师自一致性**：同一 prompt 采样 $k$ 次的一致率
2. **学生探针损失**：当前学生 checkpoint 在该样本上的 loss（学生已会的即简单题，即 *student-aware difficulty*）
3. **跨教师分歧度**：两个不同教师（Qwen3.8-27B × DeepSeek）的答案分歧

> **指标**：难度分层与真实评测表现的**相关性**（Spearman ρ）

### 6.5 子模覆盖优化 + 配比求解的数据集构造

数据选择不是"生成 10 万条直接训"：

- **去重**：embedding 聚类去重
- **覆盖**：把选择写成子模最大化（facility location），贪心算法有 $1-1/e$ 近似保证，目标是最大化 (意图 × 难度 × 槽位) 网格的覆盖
- **配比**：把目标分布（如简单 30% / 中等 50% / 困难 20%）写成带质量上限约束的小型线性规划，用水位法求解

> **指标**：同等数据量下评测得分 ↑；类别覆盖度 ↑

### 7.2 路由消融

| 策略 | 云调用占比 | P95 延迟 | 任务准确率 | 误升级率 | 误降级率 |

### 7.3 必须产出的三张图

1. **可靠性图（Reliability Diagram）**：校准前后的对比，附 ECE 数值
2. **路由权衡曲线**：横轴云调用占比，纵轴任务准确率，画出不同 $\lambda$ 下的帕累托前沿
3. **端侧热稳定性曲线**：连续推理 10 分钟，横轴时间、纵轴 decode tok/s 与温度（多数学生项目不测这个，测了就赢）

### 7.4 评测集

必须**独立于训练数据**，按 (意图 × 难度) 分层抽样，人工核验标签。规模不必大（每个格子 ≥ 20 条即可），但要覆盖全部能力契约条目。

## 9. 风险与降级预案

| 风险 | 影响 | 预案 |
|---|---|---|
| 教师 API 不返回 `logprobs` | 无法做真正的 logit 蒸馏 | 退化为"多候选采样频率近似分布"；或改用本地 27B 离线跑 top-K 落盘 |
| 8 GB 显存不够同时放教师与学生 | 训练中断 | 教师侧离线缓存 top-K logits；学生训练时显存里不驻留教师 |
| 端侧 0.6B 在中文结构化输出上崩坏 | 端侧不可用 | 语法约束解码 + 用 1.7B 兜底；最差情况端侧只做分类与路由，生成全上云 |
| 真机 ROM 后台限制（OPPO ColorOS） | 场景触发链失效 | 引导用户加白名单；降级为前台服务 + 通知 |
| NPU 链路不可用 | 性能指标难看 | CPU/GPU 路线的实测数字同样可写简历；NPU 作为"已验证可行性"的冲刺项 |
