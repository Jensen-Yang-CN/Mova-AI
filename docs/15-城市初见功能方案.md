# 城市初见：出行中的城市切换提醒

更新：2026-10-12。状态：第一版代码已接入；模拟坐标 → 高德解析 → 城市确认 → 系统通知 → 城市卡片已在 OPPO 真机验证。真实位置服务已编译，真实跨城与长期锁屏运行尚未验收。

## 产品场景

用户坐高铁或火车前往另一座城市，希望进入新城市时收到欢迎消息，并了解当地特色美食与代表性景点。产品入口命名为「城市初见」，延续 Mova·照应对离家生活的关注：初到一个地方，也有一个轻松认识它的起点。

提醒采用 App 系统通知，点击进入城市卡片，不依赖读取运营商欢迎短信。城市卡片给出少量、可核对的介绍和下一步入口，不自动发送消息或开启导航。

## 第一版闭环

```text
用户开启本次出行 → 获取位置并识别城市 → 稳定确认城市变化
    → 判断是否符合提醒偏好 → 读取城市资料 → 发欢迎通知
    → 点击城市卡片 → 查看美食 / 景点 → 用户选择后打开地图搜索
```

- 默认沿途提醒；也可选择仅武汉 / 仅岳阳作为第一版目的地筛选。目的地不等于车站，进入目标城市也不表示列车已经到站。
- 提供可选的「沿途城市」模式，实现用户提出的经过新城市边界后的欢迎提醒。
- 首次定位用作出发城市基线，不直接误判为跨城。
- 同一城市本次行程仅提醒一次；手动结束出行即停止定位。
- 城市切换确认后才发通知；不承诺行政边界处即时、秒级触发。

## 接入现有项目

客户端已补充位置权限、location 类型前台服务、城市变化检测器、通知与卡片页面，服务端新增高德坐标转换 / 逆地理编码适配及城市资料接口。模型原有 location 契约继续保留，本功能的城市检测不依赖模型推理。

本轮模块职责：

| 模块 | 职责 |
|---|---|
| Android 出行页 | 选择目的地或沿途模式、开始 / 结束行程、显示定位与通知状态 |
| 位置前台服务 | 用户在页面启动后持续获取位置，显示运行通知及停止按钮 |
| 城市解析器 | 将有效坐标转成稳定的城市标识，兼容直辖市和空字段 |
| 城市变化检测器 | 记录候选城市、连续确认、行程去重与提醒冷却 |
| 城市资料接口 / 缓存 | 自动获取美食建议、地图景点及来源，完整结果缓存 24 小时 |
| 欢迎通知与详情页 | 简短欢迎通知，点击展示完整城市卡片与地图入口 |

0.6B 模型不能代替定位服务，不负责推测经纬度或判断行政边界。第一版城市检测采用确定性规则，避免每次位置更新都跑模型。用户继续询问城市相关问题时，再考虑接入已有意图理解与云端生成。

## 定位与后台运行

推荐使用国内可用的定位 / 逆地理编码服务。高德 Web 服务提供坐标到行政区域的解析，需要单独的地图服务 Key；已有千问 Key 不能替代它。使用 Android GPS 坐标时须按服务文档处理坐标系，不能把不同坐标系直接混用。

用户在 App 可见时点击「开始出行」，授权定位后启动 location 类型前台服务；运行中保留可见的行程通知。Android 对后台启动位置前台服务有限制，不能设计成任意时刻悄悄自启。第一版不依赖开机恢复或全天后台追踪。

隧道、车厢、弱网与系统省电限制可能造成延迟或位置缺失。位置不可用时显示等待状态；可查看已保存的城市卡片，或手动提交模拟点位验证介绍流程。

## 减少误报与耗电

以下是第一版待实测的初始参数，不是已验证的性能结论：

- 移动途中按约 2–5 分钟获取 / 处理一次位置；结合位移阈值控制逆地理请求。
- 排除明显过期或精度不足的位置；具体精度阈值结合所用定位服务确定。
- 新城市至少两次有效观测确认，且跨越最小确认间隔，防止边界漂移反复触发。
- 设置提醒间隔并按行程记录已提醒城市；边界来回漂移不重复通知。
- 定位监测与欢迎提醒分开：资料请求失败不伪造景点或食物。

## 城市介绍数据

城市推荐已改成通用获取流程：武汉、岳阳保留已有政府资料；其他已识别城市由云端模型整理代表性菜肴 / 小吃与景点候选，随后在高德检索本市相关景点，过滤不相关结果和停车场等附属地点。无需逐个城市录入。美食标注「AI 城市知识整理」，景点标注「高德地图检索」；不能把餐厅存在当成菜肴起源或当地特色的证明。

推荐只给名称与简短欢迎语，不生成实时营业、票价或排名。模型暂不可用时尝试地图餐饮 / 景点候选，餐饮店明确标注为店铺，不冒充特色菜。两类来源都不可用则提示刷新重试，不能保证断网时获取新城市的介绍。

完整推荐在服务端缓存 24 小时，缓存版本变更会失效；部分或空结果不缓存，避免一次失败持续影响用户。高德请求统一间隔约 0.6 秒，避免瞬间并发导致部分查询失败；手机城市介绍等待上限调整为 45 秒。只向模型发送城市名和编码，不发送用户精确坐标。

App 打开城市页面时会补加载旧版本或空卡片，更新所有同城记录，保留原到达时间与模拟标记，不重复发通知。卡片提供「刷新城市推荐」；多城市刷新采用串行保存最新快照，避免旧快照覆盖已更新结果。

通知尽量简短，详细信息放在城市卡片；实时价格、天气、营业状态只在有相应数据源时展示。无网络时仍能查看手机上已保存的卡片，并标明更新时间；新城市没有资料时仅欢迎用户并说明介绍暂未加载。

位置识别可能需要向地图服务发送坐标，启用前应说明这点。第一版不保存完整轨迹，只保留完成检测所需的最近状态与已提醒城市；精确坐标不写入公开日志，也不默认交给语言模型。

## 验收范围

1. 用标明「模拟行程」的坐标序列验证跨城、边界抖动、直辖市和重复城市，不能冒充真实铁路测试。
2. 真机确认权限拒绝、开始 / 结束行程、锁屏运行、系统通知及点击详情；退出行程后没有持续定位。
3. 弱网 / 定位缺失时不误报到站、不循环弹通知。
4. 城市卡片资料与来源相符；目的地模式不提示途经城市。
5. 真实跨城行程再记录触发延迟与耗电；此后才能宣称高铁场景已实测。

## 现在怎样原地测试

1. 启动本地 `scene_ai_server`。已在私有 `.env` 配置 `MOVA_AMAP_KEY`，Key 不进 APK 或 Git。手机沿用已设置的服务地址；USB 联调依然需要电脑服务和反向端口映射。
2. 首页打开「城市初见」，选择「沿途城市」，切换到「原地体验」，点击「播放模拟行程」。允许通知即可，不要求定位权限或系统开发者选项。
3. 五个模拟观测依次经过武汉、武汉、岳阳、岳阳、岳阳。第二次岳阳观测确认后产生一张到达卡片 / 欢迎通知，最后一次岳阳不重复通知。每次回放是新行程，允许重新演示。
4. 点击通知，直接打开「一份城市照应」。卡片带「模拟行程」标识、食物 / 景点、来源及地图搜索按钮。
5. 若要手动测试：先结束已有行程，点击「手动模拟经纬度 →」展开输入，再输入 `114.30 / 30.60`（武汉公共示例），提交一次建立基线；改为 `113.13 / 29.37`（岳阳公共示例），连续提交两次。选择「高德 GCJ-02」；如果采用原始 GPS 坐标则选择「GPS WGS-84」。

这不是对用户实际位置的修改，不影响其他地图 App。示例点位不对应用户所在单位，也不是实际列车轨迹。模拟时间经过压缩，不能把回放耗时当作真实触发延迟。

### 手动点位没有出现欢迎通知时

- **先看识别结果**：首次有效点位只设定出发城市，后续需要另一城市连续两次有效观测才发欢迎通知。手动模式不会每隔一分钟自动提交；两次点击提交会推进模拟时间，不需要真的等待一分钟。
- **经纬度须保持正确数值与顺序**：例如本轮青岛测试用经度 `120.3844`、纬度 `36.0625`。把经度误写为 `128.3844`，高德未返回国内城市，应该修正后重新提交；这不是模型生成速度的问题。
- **请求状态与行程状态不同**：新界面单独显示点位处理中 / 手动模拟等待下一次提交，识别失败时显示明确错误，提交按钮附近也显示城市与结果。处理中禁止重复点击，避免请求排队。
- **城市介绍加载**：青岛等新城市会自动获取美食与景点，已保存的旧空卡片也会更新。若只有部分结果或出现网络错误，可点击卡片的「刷新城市推荐」。美食为 AI 城市知识建议，景点名称采用高德相关地点结果，均不代表实时营业保证。

本轮已在 OPPO 手机复测：错误经度 `128.3844` 显示失败并恢复可提交状态；修正为 `120.3844 / 36.0625` 后识别为青岛市。从武汉基线连续提交两次青岛点位，系统出现「模拟行程 · 欢迎来到青岛市」通知。脱敏记录见 `artifacts/city-v1/manual-regression.json`。

### 测试证据与代码

- Android `CityChangeDetectorTest`：4 项通过，覆盖城市确认 / 去重、边界抖动与过期观测、目的地筛选、提醒冷却。
- 服务端 `tests/test_cities.py`：8 项通过，增加通用新城市生成、直辖市 POI 过滤、停车场排除和模型失败后的地图回退。
- 通用推荐联调：青岛返回鲅鱼水饺 / 辣炒蛤蜊 / 排骨米饭及栈桥景区 / 崂山风景区 / 八大关风景区；成都通过相同流程返回美食及本市景点，不依赖城市白名单。
- 青岛首次请求约 5.147 秒，缓存请求一次约 256 ms；仅是两条服务请求实测，不是平均延迟。手机旧青岛卡片自动更新，持久化与重开显示已核验。
- 实际高德调用：武汉 / 岳阳 GCJ-02 坐标及 GPS 坐标转换路径均解析成功。
- OPPO 真机：模拟回放确认岳阳，系统通知显示「模拟行程 · 欢迎来到岳阳市」，内容含岳阳米粉 / 火焙鱼、岳阳楼 / 君山岛；已验证通知点击与卡片。
- 未测：真实跨城、长时间熄屏、耗电与跨机型后台表现。真实服务使用 Android LocationManager，约两分钟 / 500 米更新要求，过滤过期及粗糙位置；系统不保证严格周期。

代码入口：`data/city/CityChangeDetector.kt`、`CityTripManager.kt`、`CityLocationService.kt`、`CityNotifications.kt`；界面 `ui/city/CityScreen.kt`；服务端 `mova/cities.py` 和 `app.py` 的 `/city/resolve`、`/city/guide`。
