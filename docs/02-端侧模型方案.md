## 1. 能力契约：端侧 SLM 到底要学什么

这是整个项目**最先要定、也最容易做错**的一步。若不定契约，最后一定演变成"端侧模型什么都不会，只能全上云"，项目也就退化回调 API。

### 1.1 契约设计原则

端侧只学三类能力，共同点是：**输入短、输出结构化、错误代价低、调用频次高**。

| 类别 | 说明 | 为什么放端侧 |
|---|---|---|
| **感知类** | 场景分类、图像触发判定（食材/文本/无场景） | 频次最高（每次相机帧都要判），且涉及隐私图像 |
| **决策类** | 意图分类、任务难度打分、路由建议 | 输出极短（几个 token / 一个标量），端侧足够 |
| **抽取类** | 从用户输入中抽槽位、生成结构化 JSON | 有 Schema 约束，正确性可校验，错了能升级 |

**不学**：长文生成、复杂推理、多轮长上下文创作 —— 这些上云。

### 1.2 契约条目（示例，需在 S1 阶段定稿）

```jsonc
// 端侧模型的统一输出契约（由语法约束解码保证一定是合法 JSON）
{
  "scene": "food | reading | chat | location | none",   // 枚举，感知类
  "intent": "diet_advice | summarize | reply_suggest | ...", // 枚举，决策类
  "complexity": 0.42,        // [0,1] 连续，决策类 —— 直接喂给路由器
  "confidence": 0.91,        // [0,1]，模型自报 + 外部校准
  "need_cloud": true,        // 布尔，决策类
  "slots": {                 // 抽取类，按 scene 分支
    "ingredients": ["番茄", "鸡蛋"],
    "text_length": 320
  },
  "local_answer": null       // 只有 need_cloud=false 时才有内容
}
```

**为什么要让端侧直接输出 `need_cloud` 和 `complexity`？**
因为这样"路由"就是**端侧模型的一项被蒸馏出来的能力**，而不是外部写死的阈值规则。教师模型（27B）在生成训练数据时会给出它认为正确的复杂度与是否上云，端侧学的就是这个判断。这是本项目在算法上最有说服力的一点。

### 1.3 训练/评测数据的分层

按 (场景 × 意图 × 难度) 分层。难度分三档（简单/中等/困难），每档目标占比见 §2.4。评测集必须**独立于训练集**，每格 ≥ 20 条。

## 2. 数据引擎（S2）

### 2.1 教师多角色复用

同一个 27B 承担四个角色，但用**不同的系统提示与解码参数**，并且**角色之间互相校验**：

| 角色 | 职责 | 关键设计 |
|---|---|---|
| Generator | 从种子场景生成用户输入 | 用场景模板 + 真实 App 名称/时间/地点变量，保证分布贴近真实 |
| Teacher | 产出高质量答案与结构化输出 | 强制 JSON Schema 输出 |
| Judge | 评价候选答案质量 | 打分 1–5，低分样本直接丢弃 |
| Difficulty Estimator | 估计难度 | **不用它的自评结果**，只作为三信号之一（见 §2.2） |

### 2.2 三信号客观难度评估

模型自评难度校准很差，因此难度由三个**可独立测量**的信号合成：

**信号 1 · 教师自一致性**
同一 prompt 用温度 0.8 采样 $k=5$ 次，对结构化输出按字段比对：

$$
\text{consistency} = \frac{1}{k}\sum_{j=1}^{k}\mathbb{1}\!\left[\text{fields}(y_j) = \text{majority}(\text{fields}(y_{1..k}))\right]
$$

一致率越高 → 越简单。

**信号 2 · 学生探针损失（student-aware difficulty）**
用**当前学生 checkpoint** 在该样本上算交叉熵 $\ell_i$。学生已经会的题就是简单题。这一项让难度**随训练进程自适应**——早期很难的题，中期可能变简单。

**信号 3 · 跨教师分歧**
两个不同来源的教师（自托管 Qwen3.8-27B × DeepSeek API）分别作答，按字段比对。分歧大 → 该样本本身边界模糊，属于困难样本，也顺带做了质量过滤。

合成：

$$
d_i = \sigma\!\Big(w_1(1-\text{consistency}_i) + w_2\,\hat{\ell}_i + w_3\,\text{disagreement}_i\Big)
$$

$\hat\ell_i$ 为归一化后的损失；$w$ 用一小批人工标注的难度样本做逻辑回归拟合。

> **验证方式**：算 $d_i$ 与真实评测表现的 Spearman 秩相关。若相关性低于 0.4，说明难度信号无效，宁可退回朴素分档也不要留一个"看起来高级但没用"的模块。

### 2.3 去重与覆盖度优化

**去重**：用中文 embedding 模型（`bge-small-zh` 级别即可）编码全部候选，按余弦相似度做贪心聚类去重，阈值按簇内方差自适应（而非全局固定阈值）。

**覆盖度当子模最大化**：把数据集看作对网格 $\mathcal{G}=$ (场景 × 意图 × 难度 × 槽位类型) 的覆盖问题。定义覆盖函数

$$
F(S) = \sum_{g \in \mathcal{G}} \sqrt{\sum_{i \in S \cap g} q_i}
$$

（平方根形式保证**边际收益递减**，即天然抑制某类样本堆叠）。$q_i$ 是样本质量分。$F$ 单调子模，贪心算法有 $1-1/e$ 近似保证。

**为什么用平方根**：如果用线性求和，算法会把所有样本堆到样本最多的那个格子里；平方根让"补齐空白格子"的边际收益更高，自然得到均衡覆盖。这是有理论依据的选择，不是调参调出来的。

### 2.4 配比求解

目标分布（示例）：简单 30% / 中等 50% / 困难 20%。不要直接按这个比例随机抽样，因为有些格子的高质量样本根本不够。写成一个小的线性规划：

$$
\min_{x} \ \sum_i \big(1 - q_i\big) x_i
\quad \text{s.t.} \quad
\sum_{i \in g} x_i \ \ge\ n_g^{\min} \ \ \forall g,
\qquad
\sum_i x_i = N,
\qquad
0 \le x_i \le 1
$$

即"在满足每格最低配额与总量约束的前提下，最大化入选样本的平均质量"。规模小，用现成 LP 求解器即可；实现上也可以用水位法近似。

### 2.5 数据落盘格式

```jsonl
{"id":"food_000123","input":"...","output":{...},"scene":"food","intent":"diet_advice",
 "difficulty":0.72,"signals":{"consistency":0.4,"probe_loss":0.83,"disagreement":0.6},
 "quality":4.5,"teacher":"qwen3.8-27b"}
```

每条都带**可追溯的难度信号与质量分**，便于后续做数据消融（"去掉困难样本会掉多少分"）。

## 3. 三层蒸馏

### 3.1 第一层：Response Distillation（必做）

最直接：教师输出当作硬标签做 SFT（LoRA）。这是基线，也是消融表的 B 行。

### 3.2 第二层：Logit Distillation（主攻）

传统 KD：

$$
L_{KD} = T^2 \cdot \mathrm{KL}\!\left( p_T^{(T)} \,\|\, p_S^{(T)} \right),
\qquad
p^{(T)} = \mathrm{softmax}(z / T)
$$

$T$ 为温度。教师不只告诉学生"正确答案是 A"，还告诉它"B 有 0.08 的概率、C 几乎不可能"—— 这就是 dark knowledge。

#### 3.2.1 前提：tokenizer 对齐

必须选**同族模型**做教师/学生，否则词表不一致，KL 根本算不了：

| 方案 | tokenizer 对齐 | 可行性 |
|---|---|---|
| Qwen3-4B → Qwen3-0.6B | ✅ 同族同词表 | **推荐**（教师侧小、跑得快） |
| Qwen3.8-27B → Qwen3-0.6B | ✅ 同族 | 最强教师，但需要离线缓存 logits |
| Qwen3.8-27B → Gemma-3n | ❌ 词表不同 | 只能做 Response 蒸馏 |

#### 3.2.2 关键工程技巧：离线 top-K logits 缓存

学生训练时**不把教师放进显存**。流程：

```
第一阶段（教师侧，B200 或 API）
  对训练集每一条样本，逐 token 记录教师分布的 top-K：
    token_ids:  int32[K]     (K = 64)
    logprobs :  float16[K]
  落盘为分片文件
        │
        ▼
第二阶段（学生侧，本机 8GB 足够）
  训练时按 batch 读缓存 → 构造稀疏的教师分布 → 算 KL
```

**存储估算**（这是可行性依据，不是估算口号）：

| 项 | 数值 |
|---|---|
| 样本数 | 50,000 |
| 平均输出 token 数 | 256 |
| 总 token 数 | $1.28 \times 10^7$ |
| 每 token 存 K=64 的 (id, logprob) | $64 \times (4 + 2) = 384$ B |
| **合计** | **≈ 4.9 GB** |

5GB 落盘换掉“教师常驻显存”，这是让 8GB 卡也能做 logit 蒸馏的关键。若教师是**自托管**（vLLM / SGLang），可以直接取全词表 logits 再离线截断 top-K，比走 API 更完整，也不受 `top_logprobs ≤ 20` 的限制。

> ⚠️ **待验证假设**：若只能走 API，需要确认厂商是否返回 `logprobs` / `top_logprobs`。若不可用，退化为"多次采样的候选频率分布"作为软标签的近似。

#### 3.2.3 损失函数（完整形式）

$$
L = \alpha \underbrace{L_{SFT}}_{\text{硬标签}} \;+\; \beta\, T^2 \underbrace{\mathrm{KL}\!\left(p_T^{(T)} \| p_S^{(T)}\right)}_{\text{软标签}} \;+\; \gamma \underbrace{\mathcal{L}_{feat}}_{\text{特征对齐}}
$$

工程实现要点：

1. **只在 response token 上算 KL**，prompt token 全部 mask 掉（否则学生会被训练去预测用户输入，浪费容量）
2. **温度退火**：$T$ 从 4.0 线性降到 1.0。高温阶段学暗知识（分布形状），低温阶段保正确性
3. **教师分布稀疏化**：只保留 top-K 并重新归一化；未被覆盖的尾部概率质量按均匀分布摊掉，避免 KL 被无限大的惩罚主导
4. **$\alpha + \beta$ 的配比做网格搜索**，作为消融的一行

#### 3.2.4 forward KL vs reverse KL（值得单独讨论）

| | forward KL $\mathrm{KL}(p_T\|p_S)$ | reverse KL $\mathrm{KL}(p_S\|p_T)$ |
|---|---|---|
| 行为 | **mode-covering**：学生倾向于覆盖教师所有可能的输出 | **mode-seeking**：学生集中到教师概率最高的模式 |
| 结果 | 多样性好，但可能生成教师低概率的怪话 | 输出更稳、更"正确"，但多样性差 |
| 适合 | 开放生成 | **本项目的结构化输出任务** |

对 Mova-AI 这种"必须可靠地输出正确槽位"的任务，**reverse KL 或两者的加权混合**更合理。做一组 A/B 对照，这一条就能写成一个有洞察的结论。

#### 3.2.5 进阶：On-Policy / GKD

上面的做法是 off-policy（学生学的是教师在自己轨迹上的分布）。进阶做法：让学生**自己生成**序列，再由教师对该序列给出 token 级反馈。这解决了训练/推理分布不一致（exposure bias）的问题，也是当前蒸馏方向的前沿做法之一。作为 S4 的可选加强项。

### 3.3 第三层：Feature Distillation（选做）

让学生的隐状态逼近教师：

$$
\mathcal{L}_{feat} = \mathrm{MSE}\big(P(H_T), H_S\big)
$$

- 两者 hidden dim 不同（如教师 3584、学生 1024），所以必须加**投影** $P(\cdot)$
- 层数不同（如 36 层 vs 28 层），按比例做**层映射**：学生第 $i$ 层对齐教师第 $\lfloor i \cdot L_T / L_S \rfloor$ 层
- 归一化后再算 MSE，否则尺度差异会让损失被某一层主导

**优先级最低，时间不够就砍。** 简历上写"研究了 Response / Logit / Feature 三种知识迁移方式"比写"我做了蒸馏"强得多，但前提是前两层扎实。

## 4. 量化

### 4.1 先搞清楚参数都花在哪

**开训前第一件事是核对 `config.json` 里的 `tie_word_embeddings`。** 以 Qwen3-0.6B 为例，词表 151936、hidden 1024：

| 情形 | embedding 参数量 | 占总参数 |
|---|---|---|
| `tie_word_embeddings = true`（lm_head 与 embedding 共享） | ≈ 1.56 亿 | ≈ 26% |
| `= false`（两份独立权重） | ≈ 3.11 亿 | **≈ 52%** |

这一项直接决定量化预算怎么分：**如果不共享，embedding + lm_head 就是模型的一半，而对它们做 4bit 量化的收益远低于对注意力/FFN 做量化**（词嵌入量化会明显伤表示质量）。

**处理策略**：embedding / lm_head 单独用 8bit（或保持 fp16 并 tie），其余层 4bit。这个决策比"整模型一刀切 4bit"的内存表现和精度表现都好。

### 4.2 分层敏感性分析

对每一层 $l$，只量化该层、其余保持 fp16，在标定集上测输出分布偏移：

$$
s_l = \mathbb{E}_{x \sim \mathcal{D}_{cal}} \Big[ \mathrm{KL}\big( p_{\text{fp16}}(\cdot|x) \,\|\, p_{\text{量化}l}(\cdot|x) \big) \Big]
$$

$s_l$ 越大说明该层越"娇气"。经验上：**首尾层与输出投影最敏感，中间 FFN 最不敏感**。（这个结论需要用你自己的实测数据核实后再写进文档。）

### 4.3 比特分配 = 背包问题

给定总内存预算 $B$（例如 ≤ 800 MB），每层可选 4bit 或 8bit：

$$
\min_{\{b_l\}} \sum_l \mathbb{1}[b_l = 4]\cdot s_l
\qquad \text{s.t.} \quad \sum_l \mathrm{size}(l, b_l) \le B
$$

这是标准 0/1 背包，层数只有几十，DP 或按 $s_l / \Delta\mathrm{size}_l$ 贪心即可精确求解。

> **这一段是简历上最值钱的内容之一**：把"量化"从"跑个脚本"变成"在内存约束下求解最优比特分配"。而且它有明确的、可报告的数字（各层比特分布、总 KL 上升了多少）。

### 4.4 KV cache 量化

端侧长上下文的第一杀手不是权重而是 **KV cache**：

$$
\text{KV 内存} = 2 \times L \times H_{kv} \times d \times \text{seq} \times \text{bytes}
$$

以 Qwen3-0.6B 量级（$L=28$，GQA 后 KV 头数较少）在 2048 上下文下，fp16 的 KV cache 就有几十 MB 量级，4bit 量化可再降 4 倍。用 **per-channel scale 的 int8/int4**，并报告 1024 / 2048 / 4096 三档上下文下的内存与速度。

### 4.5 量化方法对照

| 方法 | 类型 | 优点 | 缺点 |
|---|---|---|---|
| GPTQ | PTQ，逐层重建误差最小化 | 生态成熟，llama.cpp 支持好 | 需要标定集，校准顺序敏感 |
| AWQ | PTQ，按激活重要性保护显著权重 | 通常精度优于 GPTQ | 实现略复杂 |
| QAT（LSQ 式可学习 scale） | 训练中量化 | 精度天花板最高 | 成本高，只对高敏层做 |

**建议**：主体用 AWQ/GPTQ，对敏感性 top-3 的层补做 QAT。这条"混合策略"本身就是个不错的结论。

### 4.6 评测量化损失

必须报告：量化前后在**分层评测集**上的准确率变化、JSON 合法率变化、以及 KL 散度。**只报体积不报精度是耍流氓**，面试官一定会问"精度掉了多少"。

## 5. 端侧运行时

### 5.1 目标机

**OPPO Find X7 Ultra · 骁龙 8 Gen 3**：Hexagon NPU 可用，意味着存在"绕过 CPU 直通 NPU"的路线。这对投 OPPO 的岗位是极强的对口信号。

### 5.2 候选路线

| 路线 | 是否需要 NDK | 优势 | 定位 |
|---|---|---|---|
| **llama.cpp（GGUF）** | 需要（NDK + CMake） | 量化格式最全（Q4_K_M / IQ4_XS）、CPU/GPU offload、社区最活跃、面试官最认 | **主线** |
| **LiteRT-LM / MediaPipe LLM Inference** | 不需要（纯 Gradle AAR） | 集成最快，自带 GPU delegate | **横评对照** |
| MNN-LLM（阿里） | 需要 | 国内移动端落地最多（淘宝/钉钉同源） | 选做 |
| ExecuTorch + QNN EP | 需要 | **直通 Hexagon NPU** | **冲刺** |

**横评本身就是产出**：同一模型、同一评测集，在两条运行时上的 TTFT / decode tok/s / 峰值内存对比，比只报一条路线的数字有说服力得多。

### 5.3 语法约束解码（这一步收益极高，成本极低）

端侧 0.6B 模型最大的工程问题不是"答得不好"，而是**格式崩坏**——自由解码下 JSON 合法率可能只有六七成。

解法：用 **GBNF 文法 / JSON Schema** 约束解码，让采样过程只能在合法 token 上走。llama.cpp 原生支持 GBNF；其他运行时可用 logits processor 实现。

> 效果：JSON 合法率 → **100%**，且不需要重试。这一个改动就能把端侧从"demo 级"提升到"可用级"，是性价比最高的一处投入。

### 5.4 性能工程

| 手段 | 收益 |
|---|---|
| **前缀 KV 复用** | 系统提示 + 能力契约部分固定不变，复用其 KV，省掉每次重复 prefill |
| **prompt 压缩** | 长聊天记录/长文章先做抽取式压缩再上端侧 |
| **投机解码** | 用 n-gram / prompt-lookup 做 draft，端侧小模型验证，纯本地加速 |
| **线程与 offload 调优** | 大核绑定、Adreno GPU offload 层数扫描（offload 层数 vs 速度的曲线本身就是一张好图） |
| **动态上下文裁剪** | 按需截断历史，控制 KV 增长 |

### 5.5 测量协议（必须固化，否则数字不可信）

- **TTFT**（首 token 延迟）、**prefill tok/s**、**decode tok/s**，各测 ≥ 30 次取 P50 / P95
- **峰值内存**：`dumpsys meminfo` 或 `Debug.getPimpped...`，区分 Java heap 与 native
- **热稳定性**：连续推理 10 分钟，每 30 秒采样一次 tok/s 与温度，画曲线
- **耗电**：`BatteryStats`，报告每 100 次推理的 mAh
- **冷启动**：模型加载耗时（这是端侧体验的隐形杀手，别忘了测）

## 6. 端云路由

### 6.1 置信度必须校准

小模型的 softmax 输出**系统性过度自信**。直接用它的概率做阈值必然出错。

**做法**：在验证集上拟合温度 $T^*$ 最小化负对数似然：

$$
T^* = \arg\min_T \ -\sum_{i} \log \mathrm{softmax}(z_i / T)_{y_i}
$$

或直接做**等渗回归**（isotonic regression）得到单调校准映射。**指标用 ECE**：

$$
\mathrm{ECE} = \sum_{m=1}^{M} \frac{|B_m|}{n} \Big| \mathrm{acc}(B_m) - \mathrm{conf}(B_m) \Big|
$$

（按置信度分 $M=15$ 个等宽桶。）

### 6.2 代价敏感决策

$$
\text{端侧足够} \iff p_{\text{edge}} \ge p_{\text{cloud}} - \lambda (L_{\text{cloud}} - L_{\text{edge}}) - \mu C_{\text{cloud}}
$$

**$\lambda$ 怎么标定**（这一步是"有理有据"的关键）：
在验证集上扫描不同的 $\lambda$，得到一组 (云调用占比, 任务准确率) 点，画出帕累托前沿；由产品需要选择的准确率下限反推出 $\lambda$。**$\lambda$ 是一个由实验确定、有明确物理含义的量（每毫秒延迟愿意付出的精度代价），而不是凑出来的常数。**

### 6.3 任务级投机执行

```
端侧推理 → 语法约束解码（保证合法 JSON）→ Schema 校验
                                              │
                            ┌─────────────────┴─────────────────┐
                          通过                                不通过
                            │                                   │
                    直接返回结果 + 记录                       升级云端（不重试端侧）
```

关键设计：**校验失败不重试端侧**。因为重试的期望收益低（同一个模型同一种失败模式），而延迟翻倍。直接升级，且把升级原因记录下来展示给用户（"端侧槽位校验未通过 → 已切换云端"）。

### 6.4 进阶：端云投机解码

端侧小模型做 draft，云端大模型**一次前向并行验证** $k$ 个 draft token，接受前缀、拒绝处重采样。理论上在保持云端质量的前提下显著降低有效延迟（受网络 RTT 影响，适合 RTT 低的场景）。

> 这是把"端云协同"从架构图变成**真算法**的最强一手。作为 S7 的加分项，即使只在小规模上验证也很有价值。
